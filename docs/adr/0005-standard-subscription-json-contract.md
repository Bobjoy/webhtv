# 订阅清单的字段契约（吸收社区多仓格式）

app 与订阅服务端共用的 JSON 契约定为：顶层对象 `{"name": 清单名(可选), "list" | "urls": [条目]}`——两个键名都接受，`urls` 就是社区多仓的原生写法，因此一份社区多仓地址不做任何转换也能被当成标准清单解析。条目字段固定为 `name` / `url` / `logo` / `remark`，仅 `name` + `url` 必填（社区多仓天然只有这两个）。条目**不带** `type`，类型由所属订阅决定。

纯文本行清单的契约：一行一条，取行首第一个空白前的 token 作为 `url`，其后 `#` 或 `//` 之后的文字作为 `name`；`name` 缺失时用 URL 的 host 兜底；空行、整行注释、以及首个 token 不像 URL 的行（分组标题等）直接跳过。

**理由**：既然 app 要认社区多仓（ADR-0001），再维护一个与它 90% 重叠的独立格式就是纯成本；把 `urls` 提升为可接受键名后，解析规则塌缩成"取 `list` 或 `urls` 里的 `{name,url}`"，一套条目模型直通 `Config`。顶层保留 `name`、条目保留 `logo`/`remark`，是多仓没有但服务端部署者想要富字段时唯一需要扩展的地方。

**后果**：键名与字段一经发布即对外兼容契约——用户会照它手写清单，第三方会朝它归一化，改名或改结构等于破坏所有已发布的订阅地址。后续只允许新增可选字段，`list`/`urls` 双键名与 `name`/`url` 两个必填字段永久保留。`remark` 只在订阅条目界面展示，选中提交为资源地址时丢弃（`Config.notice` 是 `@Ignore`，本就不入库）；`logo` 会写入现有 `Config.logo`。
