# 订阅入口用明文授权码做客户端门禁

订阅功能默认隐藏（设置页没有「订阅」这一行）。连击设置页标题栏 5 次（2 秒滑动窗口）弹出解锁对话框，输入 4 位授权码；app 直接拉取 `webhtv-sub` 仓库里明文的 `codes.txt`，逐行比对，任一命中即写入解锁标记，提示"重启生效"并自动重启。取不到 `codes.txt` 就只提示失败，必须联网，不内置兜底码、不缓存码表。

**理由**：4 位数字只有 10000 种组合，只要校验发生在客户端，服务端存哈希还是存明文都拦不住拿到安装包的人——所以哈希方案只增加部署复杂度，不增加任何安全性。既然这层门禁的真实定位是「防止普通用户误入高级配置」而不是访问控制，就选实现与分发成本最低的那条路：一个静态文件、一次 GET、一次字符串比对。服务端校验（返回 204/200）被否，因为它要给无状态的订阅清单服务（ADR-0003）加第二条路径和状态语义，换来的安全性依然为零。

**后果**：
- 解锁标记是独立的 SharedPreferences 键，**不进备份白名单**（在 `Backup.include()` 里显式 `return false`，与 `remote_trust_` 同一写法）。换机或恢复备份后回到隐藏状态，需重新解锁——刻意如此，"解锁"是设备上的动作而不是可携带的配置。
- 写入标记必须用 `edit().commit()` 同步落盘，因为重启走 `CustomActivityOnCrash.restartApplication()`，它最终会 `killProcess`，而 `Prefers.put()` 是 `apply()`，会被杀掉。提示用 Toast + 约 1.5 秒延迟重启，否则用户看不见提示。
- 取码走 GitHub 直连，因此沿用 ADR-0006 的 GitHub 代理设置；未配置代理又处于墙内环境的用户会一直拿到"验证失败"，需要能看出是网络问题而不是码错。
- 分发的码是公开集合的成员，无法撤回、无法计数、无法区分人。日后真要管控，得换成服务端校验 + 设备绑定，届时本 ADR 作废。
