# 订阅清单解析：按内容首字符判定的白名单解析，不做网络兜底

app 解析订阅地址返回的内容时，只走两条确定式路径：**内容首个非空白字符是 `{` 或 `[` → 按 JSON 解析**（接受我们自定义的标准格式与社区多仓格式，两者条目数组键名 `list` / `urls` 都认）；**否则按纯文本行清单解析**（一行一个资源地址，`#` 之后是名称）。除此之外不认识任何格式。

**理由**：最初定的是"app 只解析自定义标准格式，第三方兼容全部推给自部署服务"。但真实世界（如 TVAPP 这类收集页）里现成的订阅清单就是两种形态——社区多仓 JSON 和 `URL + # 名称` 的纯文本行；用户最自然的动作是整段复制粘贴。只认自定义 JSON 会让功能对不愿部署服务的普通用户直接不可用，而这两种形态与我们格式的映射是无损且近乎同构的（多仓条目本来就只有 `name`/`url`）。

**备选方案（已否决）**：只认多仓 JSON 或只认纯文本行——各覆盖一半，剩下那一半仍要用户自己转；维持"唯一解析路径 + 全靠部署服务"——边界最干净，但产品价值不成立；把格式判定交给"解析失败就换下一种"的隐式回退——同一份内容可能因解析器顺序得到不同结果，错误原因也无法归因，明确禁止。

**后果**：解析层必须容忍社区数据的脏处——JSON 正文里夹 `//` 注释行、JSON 之前有注释头（Gson 默认 `lenient=true` 可吃掉注释），条目 URL 含中文域名需要编码，非 URL 的分组标题行要跳过而不是报错。返回 HTML 页面（例如 `/tv/dc` 这类其实是个网页）必须归入明确的"格式不支持/解析失败"报错，而不是静默空列表。第三方**配置 JSON**（TVBox/FongMi 单仓接口，即 `sites`/`spider` 那种）不属于清单，不在此兼容范围内——它本来就是一条资源地址。
