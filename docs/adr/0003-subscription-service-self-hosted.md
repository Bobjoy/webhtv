# 订阅服务端只交付代码，来源由部署者配置

**状态**：**已撤销（2026-10-01）** —— `serverless/webhtv-sub-deno/` 已删除，仓库内不再交付订阅清单服务。撤销理由：ADR-0004 定下"订阅地址即最终 GET 端点"后，app 直接消费社区现成清单，本模块在运行链路上没有任何调用点；它的独有价值（合并多源 + 补 `logo`/`remark`）已由 `Bobjoy/webhtv-sub` 仓库 + 每日巡检 Action 实际承担。本文保留作为该服务将来若被重建时的设计约束（来源必须写死在部署配置、绝不来自请求参数）。

历史上本条曾把交付形态从"Cloudflare + Deno 两份"收缩为只做 Deno 一份。

订阅清单服务作为仓库内可独立部署的模块交付，沿用 `serverless/` 现有布局（与 `webhtv-remote-*` 同级），本期只交 `webhtv-sub-deno`：可 `deno run` 本地跑，也可 Deno Deploy。Cloudflare Worker 形态不在本期范围，将来有人需要时按同一契约镜像即可。

服务端职责：按部署者配置的一组来源（http/https URL 列表）拉取 → 解析（含第三方格式）→ 去重 → 补齐字段 → 在固定路径上返回标准格式清单。来源列表写在模块的 `sources.js` 常量文件里，改源即重新部署；它**不来自请求参数，也不是环境变量或运行时可写接口**，因此服务端不存在"被任意用户驱使去拉任意地址"的能力，也不需要有状态存储和鉴权。

**理由**：如果来源由请求参数决定，公开无鉴权部署等于提供一个 SSRF 跳板，还要背下限流、监控、滥用治理与用户订阅行为的隐私暴露；而把来源固定在部署配置里，这两个问题同时消失，服务端也变成纯只读的静态清单——可以随意挂 CDN，也可以由任何人公开发布自己的地址供他人订阅。收缩为一份的原因：app 侧已内置兼容社区多仓 JSON 与纯文本行清单（ADR-0001），服务端的独特价值只剩"合并多源 + 补 `logo`/`remark` 富字段"，为这份小众价值维护两份同构实现不划算。

**后果**：仍要保留基本的拉取护栏（仅 http/https、响应大小与超时上限、重定向次数限制、失败来源跳过并在日志记录），因为配置写错或来源不可用是常态。想兼容某个第三方链接的人必须自己部署该服务（或等待有人发布转好的地址），这对普通用户是一道真实门槛。
