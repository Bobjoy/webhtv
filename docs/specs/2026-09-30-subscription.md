# 规格说明书：订阅（Subscription）

> **后续变更（2026-10-01）**：US-27 至 US-30 与"服务端"一节已作废——`serverless/webhtv-sub-deno/` 已删除，详见 ADR-0003 的撤销说明。app 侧解析规则的真实形态样本改放在 `app/src/test/resources/subscription/`，由 `SubscriptionParserTest` 走 classpath 读取。

日期：2026-09-30 · 术语见 `CONTEXT.md` · 决策见 `docs/adr/0001–0006`

## 1. 问题陈述

现在 app 只有一种拿到「资源地址」的方式：用户在设置页手动填一条 URL（`vodUrl` / `liveUrl` / `wallUrl` 三行，点击弹 `ConfigDialog`）。想换源就得再手抄一条 URL，而社区收集页（如 TVAPP 那类 README）发布的是**一整批候选资源地址**，用户只能靠肉眼挑、来回复制粘贴，也无法在不同批之间切换。

缺的是「订阅」这一层：一条订阅地址拉回的是**候选列表**，用户从中择一生效。术语边界已在 `CONTEXT.md` 钉死——订阅源不是资源地址，拉回来不会自动装载，必须由用户选中一条才成为资源地址。

## 2. 方案概述

- **一条新的数据来源 + 零个新的生效机制。** 订阅条目被选中时写入现有 `Config` 表并走 `SettingFragment.setConfig()` → `load()` 的既有流程（ADR-0002）。此后它就是一条普通的生效中的资源地址，历史、收藏、远程管理、备份全部照常工作。
- **订阅本身存在 Prefers 里的一条 JSON**（`SubscriptionStore`，同 `GitAccountStore` / `PlaybackWebhookStore` 族系），不进 Room，不做 DB migration。
- **拉取是手动、无缓存、无回退的。** 点「拉取」才发请求，条目不落库；失败只报错（ADR-0001 后果）。
- **订阅地址就是最终 GET 端点**：app 原样请求用户填的地址，不拼基址、不加参数，设置页也没有独立的"接口服务地址"项（ADR-0004）。
- **解析认两条确定式路径**：内容是 JSON 就按 `list` / `urls` 取条目（我们的格式与社区多仓统一，ADR-0005）；不是 JSON 就按纯文本行解析。
- **交付一个用户自部署的订阅清单服务**（本期只 Deno 一份），来源写死在 `sources.js`（ADR-0003）。
- **逻辑放 `app/src/main`，UI 只做 mobile**，leanback 本期不加入口。

## 3. 用户故事

每条可独立验证。`type` 取值沿用现有约定：0=点播 / 1=直播 / 2=壁纸。

### 3.1 入口与管理

- **US-01** 作为手机用户，我在「设置」页 `vodUrl`/`liveUrl`/`wallUrl` 所在区域下方看到新增的「订阅」一行，点击进入订阅管理页。leanback 端设置界面不变。
- **US-02** 作为用户，订阅管理页按「点播订阅 / 直播订阅 / 壁纸订阅」三段分组展示，每段末尾有「添加」；无订阅的段显示空态而不是空白。
- **US-03** 作为用户，我在点播分组点「添加」，填名称 + 订阅地址后确认，它立刻出现在点播分组里（类型由所在分组决定，我不需要另外选类型）。
- **US-04** 作为用户，名称留空时，app 用清单顶层 `name` 兜底；连顶层 `name` 也没有时用订阅地址的 host 作为显示名。
- **US-05** 作为用户，我重复添加同 `type` + 同 `url` 的订阅时，app 拒绝并提示已存在，列表不出现两条。
- **US-06** 作为用户，长按/编辑已有订阅可以改名称和地址；改地址后不保留旧地址的拉取结果。
- **US-07** 作为用户，删除一条订阅只删除订阅本身：由它提交过的生效资源地址、历史记录、收藏全部不受影响。
- **US-08** 作为用户，杀掉进程重开 app，订阅列表原样还在。
- **US-09** 作为用户，做全量备份/恢复时订阅列表跟着走（`subscription` 键进 `Backup.APP_PREFS` 白名单）；选择性同步里取消"配置"时不导出订阅。

### 3.2 拉取与解析

- **US-10** 作为用户，我在某条订阅上点「拉取」，页面进入加载态，完成后展示该订阅的条目列表（名称 + 备注，有 `logo` 时显示图标）。
- **US-11** 作为用户，我的自建清单 `{"name":"...","list":[{"name","url","logo","remark"}]}` 能正常解析出条目。
- **US-12** 作为用户，我直接粘贴社区多仓地址（`{"urls":[{"name","url"}]}`，正文夹 `//` 注释、JSON 之前有注释头）能解析出条目，不需要任何转换（Gson `lenient` 吃掉注释）。
- **US-13** 作为用户，我粘贴 `http://x.top/tv   # 饭太硬接口` 这种一行一条的纯文本清单，能解析出条目，`#` 之后的文字成为名称。
- **US-14** 作为用户，纯文本行里没有 `#` 名称时，条目名取该 URL 的 host。
- **US-15** 作为用户，清单里的空行、整行注释、以及首 token 不像 URL 的分组标题行（"单仓："、"推荐在线源："）被跳过，不报错也不显示成条目。
- **US-16** 作为用户，`url` 为空的 JSON 条目被丢弃，不显示为不可点的行。
- **US-17** 作为用户，订阅地址返回 HTML 页面（例如 `https://www.iyouhun.com/tv/dc`）时，我看到明确的失败提示，**不会**看到一个空列表被当成"这个订阅没有源"。
- **US-18** 作为用户，订阅地址是 `raw.githubusercontent.com` / `github.com` / `gist.githubusercontent.com` 且我在更新设置里配了 GitHub 代理时，这次拉取走同一个代理前缀；其他域名原样直连（ADR-0006）。
- **US-19** 作为用户，网络失败 / 超时 / 非 200 时，我看到一条提示，app 不记录任何失效状态、不禁用该订阅、下次仍可正常重试。
- **US-20** 作为用户，我第二次点「拉取」时 app 重新发请求，不给我看缓存结果。

### 3.3 择一生效

- **US-21** 作为用户，我在条目列表里点一条，它写入 `Config` 表并立刻按现有流程加载；回到设置页，对应类型的行显示这条的名称。
- **US-22** 作为用户，条目列表里与当前生效地址（`config_<type>`）相同的那条显示「使用中」标记。
- **US-23** 作为用户，我点的条目 URL 在该 `type` 下已存在于 `Config` 表时，app 复用已有那一行，不产生重复记录。
- **US-24** 作为用户，条目的 `logo` 写入 `Config.logo`；`remark` 只在条目列表展示，提交时丢弃（`Config.notice` 是 `@Ignore`）。
- **US-25** 作为用户，由订阅提交生效的点播源，其后在设置页的历史、远程管理页、备份里表现与手填的源完全一致。
- **US-26** 作为用户，提交直播订阅里的条目走 `LiveConfig.load()`，壁纸条目走 `WallConfig.load()`，与点播同一条通路，三条路径都能生效。

### 3.4 订阅清单服务

- **US-27** 作为部署者，我在 `serverless/webhtv-sub-deno/sources.js` 写一组 `{name, url, type}` 来源，`deno run` 或部署到 Deno Deploy 后，GET 该模块的固定路径返回标准格式清单。
- **US-28** 作为部署者，来源里有不可用的一项时，服务跳过它并记日志，其余来源照常出现在返回结果里，而不是整个 502。
- **US-29** 作为部署者，多个来源里重复的 `url` 在输出中只出现一次。
- **US-30** 作为部署者，我的服务返回 `Content-Type: application/json` 的标准格式，因此把它填进任何版本的 app 订阅入口都能解析，部署者不需要关心 app 版本差异。

## 4. 已定决策（勿再翻案）

| # | 决策 | 出处 |
| --- | --- | --- |
| 1 | app 内置白名单解析（JSON + 纯文本行），无隐式格式回退；第三方单仓**配置** JSON 不在兼容范围 | ADR-0001 |
| 2 | 条目选中即写入现有 `Config` 表，订阅不维护独立生效态 | ADR-0002 |
| 3 | 服务端只交付代码、用户自部署，本期仅 Deno 一份，来源写死 `sources.js` | ADR-0003 |
| 4 | 订阅地址是最终 GET 端点，不设"接口服务地址"设置项 | ADR-0004 |
| 5 | 格式契约：顶层 `{name?, list\|urls}`，条目 `name`/`url`/`logo`/`remark`，仅前两项必填，条目不带 `type`；发布后只可新增可选字段 | ADR-0005 |
| 6 | GitHub 域名的订阅拉取复用 `update_github_proxy*` 三个既有偏好键，不新增旋钮 | ADR-0006 |
| 7 | 订阅存 Prefers 一条 JSON（`SubscriptionStore`），零 Room migration，全量备份天然覆盖 | 拷问第 19 问 |
| 8 | 仅存订阅地址、手动拉取、条目不缓存；失败只报错不留状态 | 第 9、20 问 |
| 9 | 单页三段分组、逐订阅查看、逻辑入 `main`、UI 只做 mobile | 第 11、12、23 问 |

## 5. 测试决策

**主接缝（新建设的唯一纯函数接缝）**：`SubscriptionParser.parse(String content) → List<Item>`。
输入是"已经拿到手的响应体字符串"，输出是条目列表。US-11 到 US-17 全部在这一层用纯 JUnit 测（无 Android 依赖、无网络）：标准 JSON、带 `//` 注释的多仓、注释头 + 脏空白、纯文本行、名称缺省、跳过标题行、HTML 输入判失败、空 `url` 条目丢弃。断言包含条目顺序、名称、url、logo、remark。

**次接缝**：`SubscriptionStore`（Prefers CRUD）。用 Robolectric 测增删改查、重复 `type`+`url` 拒绝（US-05）、持久化重启（US-08）、以及 `Backup.include("subscription", ...)` 的白名单行为（US-09）。

**代理改写**：`GithubProxy.Config.rewrite()` 已有测试覆盖；本期只需一条断言——订阅的 host 判定函数对 GitHub 三域名返回 rewrite、对其他域名返回原值（US-18），沿用 `app/src/test/.../update/GithubProxyTest.java` 的写法。

**生效通路（US-21 至 US-26）不新建测试机制**：它复用 `Config.create(type).url().name().update()` 与 `SettingFragment.setConfig()` 这条既有路径，验收方式是 Robolectric 截图 + 真机走一遍。注意本机是 Intel Mac、产物 ABI 为 arm，**不承诺用 AVD 验证**；UI 层交给 Robolectric 截图或用户真机。

**服务端（US-27 至 US-30）**：在 `serverless/webhtv-sub-deno/test/` 里用本地 fixture 断言去重、失败来源跳过、输出结构符合 ADR-0005 契约，不发真实网络请求（HTTP 客户端注入假实现）。

**"完成"的判定**：解析器测试全绿 + 真机或 Robolectric 走完"添加社区多仓地址 → 拉取 → 点一条 → 设置页显示该名称并成功加载站点"这条金路 + 一次直播类型同路 + 一次失败场景（填 HTML 地址）看到明确报错。

## 6. 明确不做

- leanback / TV 端的任何订阅界面与遥控器交互。
- 自动更新、后台定时刷新、进页面自动拉取（第 9 问：只手动）。
- 条目缓存、失效比对、订阅"最近错误"状态、测活与可用性标注。
- 订阅分组、排序、导入导出、多端同步、账号体系。
- 把 TVBox/FongMi 的**单仓配置 JSON**（`sites`/`spider`）当订阅清单解析——它本身就是一条资源地址。
- 运行时"接收任意 URL"的归一化代理（ADR-0004 已废）、Cloudflare / Go / Rust / Vercel 形态的服务端。
- `Config` 表结构改动、Room migration、`Prefers` 键改名、`update_github_proxy*` 键名变更。
- 公开运营的服务实例与相应的限流、监控、鉴权。

## 7. 补充说明

- **界面文案要跟着语义走**：`update_github_proxy` 现在同时影响更新与订阅，`R.string.update_github_proxy` 的中文文案需改为"GitHub 代理（更新与订阅）"一类表述，键名不动以保备份兼容（ADR-0006 后果）。
- **社区清单里的中文域名**（`https://tv.菜妮丝.top`、`http://www.饭太硬.net/tv`）必须由 `HttpUrl` 做 IDN 编码后再请求；解析层拿到的是原样字符串，不要提前 `trim` 掉非 ASCII。
- **Gson 宽松模式是本期的隐式依赖**：多仓正文里的 `//` 注释靠 Gson 默认 `lenient=true` 才能解析。`SubscriptionParser` 里显式 `setLenient(true)`，别依赖默认值。
- **服务端价值已经收窄**：兼容现成清单后，`webhtv-sub-deno` 只服务"合并多源 + 补 `logo`/`remark` + 挂 CDN"这一小众需求，README 要把这一点写清楚，免得用户以为必须先部署才能用订阅。
- **原需求里的"需要开发接口服务"仍然成立**，只是它的角色从"兼容必需的运行时依赖"降级为"可选的自部署增强"。
